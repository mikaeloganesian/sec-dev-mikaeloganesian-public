# ADR-002: Стандартизация ошибок по RFC 7807
Дата: 2025-09-22
Статус: Accepted

## Context
Для повышения предсказуемости API и предотвращения раскрытия чувствительных деталей внутренней реализации (угроза **I: Information Disclosure**), необходимо унифицировать формат ответов об ошибках 4xx и 5xx. Риск **R-04** (Утечка чувствительных данных через логи) связан с неконтролируемым форматированием ошибок.

## Decision
Все HTTP-ответы об ошибках (4xx, 5xx) должны возвращаться в формате **RFC 7807 (Problem Details for HTTP APIs)** с использованием выделенной функции-обработчика.
1.  **Формат:** JSON с `Content-Type: application/problem+json`.
2.  **Обязательные поля:** `type`, `title`, `status`, `detail`.
3.  **Трассировка:** Добавление расширенного поля `correlation_id` (UUIDv4) для каждого ответа, чтобы обеспечить трассируемость (**NFR-07**).
4.  **Маскирование:** Поле `detail` не должно содержать трассировки стека, SQL-запросов или чувствительных переменных.

**Параметры:**
* `correlation_id`: генерируется `uuid4()`.
* `type`: по умолчанию `"about:blank"`, но должен быть специфичен для известных ошибок.

## Consequences
**Плюсы:**
* **Снижение R-04 (Уровень риска: 2):** Контролируемое маскирование деталей (предотвращение Disclosure).
* **Улучшение DX:** Клиенты (Фронтенд P2) могут надежно обрабатывать ошибки, проверяя заголовок и `type`.
* Упрощение аудита и мониторинга благодаря `correlation_id` (**NFR-07**).

**Минусы:**
* Необходимость создания/настройки глобального обработчика ошибок (middleware) для перехвата всех исключений в Бэкенде (P3).

## Alternatives
- Кастомный формат JSON-ответа
- Использование стандартных исключений FastAPI без перехвата
